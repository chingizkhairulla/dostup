# Личные чаты и выдача доступа

После фактического открытия доступа создаётся один личный чат на пару продавец–покупатель. История остаётся доступной после окончания доступа и удаления продукта. У продавца вкладка «Все» содержит активных покупателей; «Неактивные» — покупателей без доступа ко всем его продуктам. Статус пересчитывается при загрузке списка и каждые 5 секунд, без задания cron.

Настройка продукта `after_access_enabled` / `after_access_url` доступна продавцу. Она исключена из публичных колонок каталога и checkout. Ссылка должна быть абсолютной HTTPS без логина/пароля; проверяется в форме, Edge Function и базе. Текст приглашения отправляется от продавца в существующий чат один раз на выдачу доступа. Повторные запросы подтверждения не дублируют сообщение. Для подписки доставка ждёт открытого периода. Миграция восстанавливает только чаты старых покупателей, без исторической рассылки приглашений.

Вкладка личных чатов и навигация показывают непрочитанные сообщения. Счётчики обновляются атомарным триггером; подтверждение чтения содержит ID показанных сообщений и не снимает бейдж с новых, ещё не показанных сообщений. Скрытый мобильный чат и фоновая вкладка не подтверждают чтение. Новые таблицы и RPC доступны только service role, после проверки пользовательской сессии в Edge Functions.

Перетаскивание работает на всей области открытого чата/канала, используя ту же загрузку, отмену и ограничения, что кнопка вложений: до 10 файлов, документы/фото до 50 МБ, видео до 500 МБ перед сжатием. Покупатель загружает в личные чаты; каналы публикует продавец. Файлы добавляются в черновик и отправляются кнопкой сообщения.

Подсказка установки показывается один раз на профиль при первом посещении сообщений, со ссылкой на существующую страницу установки. Отметка хранится на сервере, локальная отметка предотвращает повтор при навигации. В установленном приложении и у модератора подсказки нет.

## Применение после проверки PR

1. Применить миграцию `20261008154130_messages_access_and_onboarding.sql` штатным процессом Supabase.
2. Опубликовать Edge Functions `manage-products`, `direct-messages`, `messenger-state`, `support-api` (включая изменённые shared-модули). Для `messenger-state` добавлен `verify_jwt = false`: вместо JWT функция проверяет существующие сессии приложения через `resolveCaller`.
3. Опубликовать клиент. Один деплой Vercel не применяет SQL и Edge Functions.
4. Проверить покупку/подтверждение, ссылку и бейджи с двумя тестовыми профилями на staging, загрузку в приватное хранилище и S3.

## Приветствие техподдержки — отдельный запуск

Кампания `support_welcome_v1` по умолчанию **выключена**. Миграция не отправляет приветствия. Не включать рассылку в deploy hook.

После отдельного решения о запуске задать `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` только в серверной среде, затем:

```sh
npm run support:welcome
```

Это только dry-run: выводит количество кандидатов и уже обработанных профилей, без сообщений и изменения флага. После проверки аудитории:

```sh
npm run support:welcome -- --send --activate
```

Команда включает приветствия для новых профилей и обрабатывает существующих порциями по 200. Повторный запуск `--send` безопасен: уникальный ключ кампании и профиля, запись сообщения и счётчика выполняются в одной транзакции. Отчёт содержит sent/skipped/errors; после сбоя повторный запуск продолжает оставшихся. Демопрофили, служебные профили без auth identity и модератор исключены.

## Проверки

`npm run test:messages` запускает проверки URL, лимитов и активности, а также исполняет миграцию и триггеры в локальном PostgreSQL через PGlite. Проверяет выдачу/повтор/отзыв доступа, отложенную подписку, гонку чтения, идемпотентность приветствия и права ролей. Это изолированная схема с полями, используемыми миграцией; она не заменяет staging-проверку Supabase Auth, Storage и S3.

Будущая настраиваемая авторассылка после раздела «когда пользователи начнут оставаться» не включена в эту задачу.
