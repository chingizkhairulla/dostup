# Active Context

## Current Focus: English language (RU/KK/EN) + settings renames + white-on-orange
**The dark theme is cancelled** — the user dropped it 2026-09-22 ("темная тема не нужна нужен только перевод на англ"). Everything about "Подсветка", a black palette, `ThemeProvider`, and the prototype-approval gate from the first plan is out of scope; `next-themes` stays installed but unused. Branch was renamed from `темная-подсветка` to **`английский-язык`** to match. Level 4, VAN → PLAN (6 phases, down from 8 — no gated theme phase) → **CREATIVE complete**, next is `/build`. Full plan, audit and risk table in `memory-bank/tasks.md`; the two design docs are `memory-bank/creative/creative-i18n-architecture.md` and `creative-taxonomy-english.md`.

Two creative decisions to carry into the build. **C1:** inline `l({ru,kk,en})` helper (with the existing 615 `t()` calls kept), a required `en` field so an untranslated site cannot compile, and the **Cyrillic invariant** (no `en:` value contains Cyrillic) as the measurable definition of done. The real count is 730 sites, and 155 of them are KK-first with inverted operands — so the codemod runs as **two separate passes**, because one regex over both forms would silently swap Russian and Kazakh with a green typecheck. **C2:** the taxonomy migration is **cancelled** in favour of a client-side slug→EN map — search matches only title/headline/seller name and filters by slug, never by category name, the tables are seed-only config, and `20260917120000` is still unapplied, so the migration was pure production risk for 40 constant display strings. Preset product topics deliberately stay Russian (they are stored as free text in `products.topic`, so translating them would fragment the `topics` table and break `aiCategory.ts` matching).

English is to be done "all at once" per the user (they now have DB access) — UI strings + category/taxonomy names (needs a migration) + server-generated notification text (currently Russian-only, which already under-serves Kazakh users too). DB/edge-function changes are only ever prepared as files here; the user applies them, since `supabase/config.toml` points at production. The user also explicitly wants the 3-language setup to stay extensible going forward, so `Language` is built around one `LANGUAGES` list rather than one-off ternaries, specifically so a 4th language later is a small change, not another 42-file hunt.

Audit: white-on-orange is mostly already correct — 3 real defects found (`dropdown-menu` SubTrigger, `dialog` close ×, `calendar` range cell), plus two competing oranges in the code (`#FF6B00` vs the `--primary` token `#F97015`) that should unify. Honest finding for the user: white text on this orange is only ≈2.86:1 contrast, below WCAG AA (4.5:1); default taken is to keep the brand colour and make the text bold/≥16px rather than darken the brand orange, since nobody asked for a brand-colour change.
